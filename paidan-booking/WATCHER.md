# 消息值守

在后台左下角打开「设置」，可修改当前所选届次的单价，也可以开启全局消息值守。手机端先打开左上角导航菜单。

值守默认关闭，通知地址、机器人凭据全部留空。开源代码不含作者的通知渠道、客人信息或存档。

## 开启

1. 开启「脚本值守」，选择通知渠道，填写自己的接收配置。
2. 勾选需要的提醒：新预约、取消预约、客人付款通知。
3. 点击「预览并确认」，核对后再保存。
4. 点击「测试已保存渠道」，再次确认后发送一条不含客人信息的测试消息。

值守覆盖各届新发生的操作，不补发开启之前的订单。它在服务端运行，不要求管理页面保持打开。客人付款通知只表示客人点击了付款告知，仍需摄影师核对到账。

## 通知渠道

| 渠道 | 填写内容 |
| --- | --- |
| 通用 Webhook | 接收 JSON 的公网 HTTPS 地址；接收端需要时填写 Bearer Token |
| 企业微信 | 企业微信群自定义机器人的 Webhook 地址 |
| 飞书 | 飞书群自定义机器人的 Webhook 地址 |
| Telegram | 自建机器人的 Bot Token 和接收人的 Chat ID 或群组 Chat ID |
| 邮件 | Resend API Key、已验证域名下的发件邮箱、一个收件邮箱 |

### 邮件设置

邮件渠道当前使用 Resend 发信，不需要常驻电脑。先在自己的 Resend 账号验证发件域名并创建具有发送权限的 API Key，然后在「设置 → 脚本值守 → 邮件」填写：

- **API Key**：Resend 提供的 `re_…` 密钥，不是邮箱登录密码或 QQ 邮箱授权码。保存后读取设置不会显示密钥；留空保留原值。
- **发件邮箱**：例如 `notice@your-domain.com`，须属于该账号已验证的发件域名。这里仅填一个邮箱地址，不附加显示姓名。
- **收件邮箱**：接收提醒的一个邮箱，可使用 QQ、163、Gmail 等。首次配置没有预填的地址。

核对发件与收件地址，二次确认保存，再发送测试邮件。系统显示“邮件服务已接受”代表发送接口已接受请求，实际送达需检查收件箱、垃圾邮件及服务端邮件日志；不代表收件人已收到或已阅读。

邮件使用纯文本，包含通知类型、届次、CN、时段和订单号，不包含手机号、参考图或付款凭证。自动重试使用相同的消息编号作为幂等键，减少重复发送。发送权限、域名验证、额度等问题会显示通用失败提示，接口不会回传密钥。

本版没有直接连接 QQ/163 的 SMTP 授权码功能；它们可作为收件邮箱。实际发信规则与费用以所用服务为准。[Resend 发件域名设置](https://resend.com/docs/dashboard/domains/introduction)、[发送接口](https://resend.com/docs/api-reference/emails/send-email)、[重试去重说明](https://resend.com/changelog/idempotency-keys)。

邮件渠道已做配置校验、模拟接口响应、自动重试和电脑／手机界面验证；未填入真实发信凭据前，不视为已完成实际送达验证。

飞书机器人如果设置了关键词校验，请允许「拍摄排单」。目前不支持飞书签名校验；需要签名或其他聊天工具时，可使用自己控制的通用 Webhook 中转适配。Telegram 接收人需要先启动机器人，群组则需要加入机器人并赋予发送权限。

地址和 Token 保存在服务端，读取设置时只返回「已保存」状态。输入框留空会保留原值；勾选清除选项可以清掉旧地址和凭据。切换渠道会清除旧渠道凭据。配置变更采用版本检查，避免两个管理页面互相覆盖。

修改或关闭值守均需二次确认；保存设置会清空尚未发送的旧队列，之后的新通知按新配置发送。已发送的消息无法撤回。请使用自己控制的渠道，妥善保管管理密钥。

## Webhook 消息示例

```json
{
  "id": "消息唯一编号",
  "type": "booking",
  "text": "拍摄排单 · 新预约\n…",
  "event": { "name": "自己设置的届次名称" },
  "order": { "id": "订单编号", "cn": "客人 CN", "date": "5月1日", "time": "12:30-13:00" }
}
```

`type` 为 `booking`、`cancel`、`payment` 或 `test`。接收端应在成功接收后返回 HTTP 2xx；建议按 `id` 去重。通知包含 CN、日期、时段和订单编号，不包含手机号、参考图、付款凭证或后台管理链接。

## 运行与排错

- 预约保存和通知入队在同一事务内完成。网络重试生成的同一订单不会重复入队，同一订单重复点击付款通知也只提醒一次。
- 发送失败会逐步延迟重试，每条最多尝试 5 次；最终失败数和最近错误显示在设置面板。每次最多处理 5 条，待发送上限 500 条，超出部分会计入溢出数量。
- 网络结果不明确或运行进程中断时仍可能重复投递，因此通知渠道的接收端应支持去重。值守不替代后台订单记录。
- 企业微信、飞书和 Telegram 除 HTTP 状态外，还检查返回的业务成功状态。失败详情不会回传含 Token 的请求地址。
- 测试消息使用已保存配置，两次测试至少间隔 30 秒。
- 本版不包含网站在线检测、定时汇总、自动核款或催款。

仓库部署示例使用持久化对象的后台 alarm 驱动队列，不需额外 Cron 或常驻电脑脚本。移植到其他服务器时，可让任务队列或定时任务调用相同通知处理逻辑，同时保留事务、鉴权、去重和失败重试。

实现位于 [watch-runtime.js](./watch-runtime.js)，由 [backend.js](./backend.js) 在保存订单时接入。

接口参考：[后台 alarm](https://developers.cloudflare.com/durable-objects/api/alarms/)、[企业微信群机器人](https://developer.work.weixin.qq.com/document/path/91770)、[飞书自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)、[Telegram Bot API](https://core.telegram.org/bots/api#sendmessage)。
